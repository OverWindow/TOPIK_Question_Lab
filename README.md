# TOPIK II PBT·IBT 문제 생성 Lab

현재 실행 진입점에서는 사이드바의 `TOPIK II 읽기`와 `TOPIK II 듣기` 중
작업 영역을 선택할 수 있습니다. 기존 읽기 원본과 `data/types` 데이터베이스는
그대로 사용하며, 듣기 데이터는 `data/listening` 아래에 별도로 저장됩니다.

사이드바의 `백업·복원`에서는 읽기·듣기 유형 DB, 인식 결과, 생성·검수 기록,
시각 자산과 선택적인 원본 PDF/HTML을 ZIP으로 백업할 수 있습니다. 복원 전에
현재 상태의 안전 백업이 `backups` 폴더에 자동 생성됩니다.

듣기 앱은 스캔형 듣기 통합 PDF를 페이지 이미지로 렌더링하고, 1~50번을
21개 유형으로 나누어 기출 검토, 유형 분석, ChatKHU·DeepSeek 병행 생성,
검수와 자산 포함 내보내기를 지원합니다. `문제 일괄 생성`에서는 실제 음원·이미지 생성과 S3 저장, 로컬 PostgreSQL 자동 등록도 지원합니다.

## IBT 읽기·듣기 생성

`문제 일괄 생성`에서 시험 형식을 `IBT`로 선택하면 읽기 또는 듣기를 각각 30문항 생성합니다. 기본값은 기존 PBT 50문항입니다. 영역별 작업 화면에서도 시험 형식을 선택해 유형별 생성·검수·내보내기를 진행할 수 있습니다.

- `IBT/type_mapping.json`의 번호·질문 역할·공유 지문·시각 자료 규칙을 읽습니다. 생성 시 규칙과 매핑 해시를 저장하므로 실패한 작업을 재시도할 때 당시 구성을 유지합니다.
- 승인된 PBT 예시를 참고하되 IBT 유형별 차이를 적용합니다. 사진의 공식 정답과 듣기 원본 대본·음원은 미확인 상태이며 자동 승인 예시로 가져오지 않습니다. 상세 차이와 미확인 사항은 `IBT/type_mapping_notes.txt`에 있습니다.
- IBT 생성 문항은 TXT·JSON·CSV로 내보낼 수 있습니다. 원본 비교 PDF는 IBT 원본 전사·정답·대본이 없어 제공하지 않습니다.
- 듣기는 독립 문항 대본을 1회, 두 문항이 공유하는 대본을 2회 재생합니다. 총 22개 음원 그룹이 30문항에 연결됩니다.
- 읽기 4~6번 광고·표어와 7번 복합 도표는 코드로 이미지를 렌더링합니다. 듣기 1~2번은 각 네 개의 시각 선택지를 사용합니다.
- SQLite는 기존 유형별 구조를 재사용하며 IBT 기록을 `ibt_*.db`에 구분해 저장합니다. PostgreSQL은 기존 `items`, `question_sets` 테이블에 `exam_format`을 추가합니다. 기존 데이터는 `pbt`로 유지하고 시험 형식별 세트 번호·문항 수·미디어 연결을 검사합니다.

기존 PostgreSQL에는 `010_exam_format.sql`과 `011_item_audio_only.sql`이 필요합니다. 음원 연결은 `item_audio_bindings` 하나로 통합하며, 세트 없는 문항도 문항 ID로 연결합니다. 문항당 현재 연결은 최대 하나이고, 교체 전 연결은 고유 `binding_id`와 생성 시각을 유지해 보관합니다. 이관한 과거 세트 연결은 `origin_set_id`·`origin_position`에 당시 위치를 남기며, 알 수 없는 과거 문항 해시는 `NULL`로 보존합니다. 현재 연결을 조회할 때는 `is_current`와 문항의 `content_hash`를 함께 확인합니다.

011은 테이블 제거를 포함하므로 앱 시작 시 자동 적용하지 않습니다. 미적용 상태이면 작업 시작·재개를 중단하고 수동 이관을 안내합니다. 아래 명령은 선택한 로컬 DB의 쓰기를 잠그고, 일관된 전체 백업을 `backups/postgres/`에 저장·검사한 후 연결 이관, 기존 문항·세트·미디어 및 전체 연결 기록 검증, `question_set_item_audio_bindings` 제거를 한 트랜잭션으로 수행합니다. 실패하면 커밋 전 변경을 롤백합니다. 두 설정이 서로 다른 DB를 가리키면 각각 실행합니다.

```powershell
.\.venv\Scripts\python.exe -m topik_question_lab.maintenance.item_audio_migration --database-env DATABASE_URL
.\.venv\Scripts\python.exe -m topik_question_lab.maintenance.item_audio_migration --database-env QUESTION_BANK_LOCAL_DATABASE_URL
```

현재 유효한 세트 음원 연결을 우선 유지하고, 세트 연결이 없을 때 유효한 문항 연결을 사용합니다. 기존 음원 파일과 문항 내용은 변경하지 않습니다. 신규 API·업무 테이블·의존성은 없습니다.

`016_exam_track_v4_only.sql`부터 음원의 기본값과 허용 버전은 `exam_track_v4`이며, `script_snapshot`은 필수입니다. 구버전 음원이 남아 있으면 적용을 중단합니다. 백업 후 사용 여부와 연결 이력을 검토하여 별도로 정리해야 하며, 이 마이그레이션은 음원 레코드·연결 이력·원격 파일을 삭제하지 않습니다.

> 아래 내용은 읽기 영역의 기존 기능과 데이터 구조에 대한 설명입니다.

TOPIK II 읽기 기출을 유형별로 수집·검토하고, 여러 ChatKHU 모델로 유형 분석과 새 문항 생성을 비교하는 로컬 Streamlit 앱입니다. 별도 파인튜닝 대신 승인된 기출 예시와 편집 가능한 유형 분석서를 매 요청에 제공하는 few-shot 방식으로 작동합니다.

## 주요 기능

- `1~50번`을 18개 출제 유형으로 분리해 수집합니다. 저작권 사유로 지문이 공개되지 않은 문항만 자동으로 제외합니다.
- 기출, 프롬프트, 모델 실행 원문, 생성 결과와 사람 평가를 유형별 SQLite DB에 저장합니다.
- 3~4번 문제에서 누락된 밑줄 위치를 `[[밑줄 부분]]` 또는 별도 입력란으로 직접 지정할 수 있습니다.
- ChatKHU 전체 허용 모델을 동기화하고 유형마다 비교할 모델을 선택할 수 있습니다.
- 기본 비교 모델은 GPT-5.6 Luna, Claude Haiku 4.5, Gemini 3.5 Flash입니다.
- 기출 저장과 생성 문제 평가가 끝나면 자동으로 다음 문제로 이동합니다.
- 승인된 생성 문제를 TXT, JSON, CSV로 내보냅니다.
- 승인 문항을 모델·영역별 1~50번 세트로 검증해 PostgreSQL 문항 은행에 발행합니다.
- 원본 문제와 선택한 모델 A·B의 생성 문제를 나란히 배치한 3열 비교 PDF를 만듭니다.

## ChatKHU 사용

### 웹 수동 모드

API 키 없이 사용할 수 있는 기본 방식입니다.

1. 앱에서 모델과 문제 유형에 맞게 완성된 프롬프트를 확인합니다.
2. [ChatKHU](https://chat.khu.ac.kr)에서 같은 모델을 선택해 프롬프트를 실행합니다.
3. 모델의 JSON 응답을 앱의 응답 입력란에 붙여넣습니다.
4. 검증 후 분석 또는 생성 결과로 저장합니다.

### Gateway 자동 호출

조직에서 Gateway 키 발급을 허용한 경우 `.env.example`을 `.env`로 복사하고 키를 입력합니다.

macOS:

```bash
cp .env.example .env
```

Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

`.env`:

```dotenv
CHATKHU_API_KEY=발급받은_키
CHATKHU_BASE_URL=https://factchat-cloud.mindlogic.ai/v1/gateway
CHATKHU_WEB_URL=https://chat.khu.ac.kr
```

키는 UI나 DB에 저장되지 않습니다. Gateway 크레딧은 사용자가 분석 또는 생성 실행 버튼을 눌렀을 때만 사용됩니다. 사용 가능한 모델과 크레딧 정책은 계정과 조직 설정에 따라 달라질 수 있습니다.

사이드바의 `모델 선택`을 누르면 다음 기능을 사용할 수 있습니다.

- ChatKHU 전체 허용 모델 동기화
- 모델 이름 또는 ID 검색
- 복수 선택, 전체 선택과 선택 해제
- 목록에 없는 모델 ID 직접 추가

모델 선택은 유형 DB별로 저장됩니다. 이미 사용자가 저장한 선택은 기본 모델 목록이 변경되어도 유지됩니다.

### DeepSeek 공식 API

DeepSeek은 ChatKHU에 포함되지 않으므로 공식 API에 직접 연결합니다. 앱의 모델 선택 모달에서 `DeepSeek V4.1 Flash`, `DeepSeek V4 Flash`, `DeepSeek V4 Pro`를 선택할 수 있으며, 자동 호출에는 ChatKHU 키와 별도로 `DEEPSEEK_API_KEY`가 필요합니다.

1. [DeepSeek Platform API Keys](https://platform.deepseek.com/api_keys)에 로그인합니다.
2. 새 API 키를 발급하고 필요한 경우 플랫폼에서 API 잔액을 충전합니다.
3. 프로젝트 루트의 `.env`에 다음 값을 추가합니다.

```dotenv
DEEPSEEK_API_KEY=발급받은_키
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_WEB_URL=https://chat.deepseek.com
```

4. 앱을 재시작하고 사이드바의 `모델 선택`에서 사용할 DeepSeek 모델을 추가합니다. `50문제 일괄 생성`에서도 같은 모델을 선택할 수 있습니다.
5. `유형 분석` 또는 `문제 생성`에서 DeepSeek을 선택해 실행합니다.

V4.1 Flash의 공식 모델 ID는 `deepseek-flash`이며, 네 가지 생성 프리셋을 모두 지원합니다. 기존 V4 Flash의 ID `deepseek-v4-flash`는 [공식 변경 이력](https://api-docs.deepseek.com/updates/)에 따라 V4.1 Flash로 임시 연결되는 호환 별칭입니다. V4 Pro는 `deepseek-v4-pro`를 사용합니다. 유형별 화면에서는 여러 모델을 선택해 같은 프롬프트로 비교할 수도 있습니다.

DeepSeek 공식 API는 유료이며 ChatKHU 크레딧과 별도로 과금됩니다. 키는 `.env`에서만 읽고 UI나 DB에는 저장하지 않습니다. 앱은 사용자가 API 실행 버튼을 눌렀을 때만 요청합니다.

### BizRouter 문제 생성

ChatKHU와 별도로 BizRouter의 텍스트 모델을 읽기·듣기 개별 및 일괄 생성에 사용할 수 있습니다.
프로젝트 루트 `.env`에 아래 설정을 추가하고 앱을 재시작합니다. 키는 UI나 DB에 저장하지 않습니다.

```dotenv
BIZROUTER_API_KEY=발급받은_키
BIZROUTER_BASE_URL=https://api.bizrouter.ai/v1
```

1. 읽기·듣기의 `모델 선택`에서 `BizRouter 텍스트 모델 동기화`를 누르고 사용할 모델을 선택·적용합니다.
2. `문제 생성`의 `생성 서비스`를 `BizRouter`로 선택하고 생성 버튼을 누릅니다. `모든 서비스`에서는 ChatKHU와 함께 비교할 수 있습니다.
3. 일괄 생성은 `모델 목록 관리`에서 동기화한 뒤 `생성 서비스 → BizRouter`, 모델, 프리셋을 선택합니다. 서비스·모델 선택은 저장됩니다.

모델 목록은 인증된 `GET /v1/models`의 `models` 배열에서 텍스트 입출력 모델만 가져옵니다.
실제 요청은 `POST /v1/chat/completions`로 보내며 카탈로그의 모델 ID를 그대로 사용합니다.
생성 기록은 `bizrouter:` 접두사가 있는 내부 식별자로 기존 ChatKHU·DeepSeek 기록과 구분합니다.
동기화한 지원 정보에 따라 출력 토큰 한도와 추론 강도를 적용하고, 모든 활성 경로가 지원하는 경우에만 JSON 모드를 사용합니다.
Anthropic 계열이나 JSON 모드를 지원하지 않는 모델은 JSON 출력 지시와 기존 문항 검증을 사용합니다.
지원 정보를 확인할 수 없는 직접 추가 모델은 프리셋의 프롬프트 지시만 적용합니다.
일괄 생성은 모델 지원 정보를 작업 스냅샷에 보관해 재시도에서도 동일하게 사용합니다.

BizRouter 호출은 해당 계정에 별도로 과금됩니다. 음원·이미지 생성, 이미지 전사, S3 저장은 기존 경로를 사용합니다.
일괄 생성의 `음원·이미지 생성 및 DB 자동 등록` 옵션도 기존 방식대로 동작합니다.
관련 문서: [인증](https://bizrouter.ai/docs/authentication), [모델 목록](https://bizrouter.ai/docs/models), [Chat Completions](https://bizrouter.ai/docs/chat-completions).

## 50문제 일괄 생성

사이드바의 `50문제 일괄 생성`에서 모델 하나와 생성 프리셋 하나를 고른 뒤
`듣기 50문제 생성` 또는 `읽기 50문제 생성`을 누릅니다. 듣기 21개 유형,
읽기 18개 유형을 순서대로 호출해 1~50번을 각각 한 문항씩 저장합니다.
자동 실행에는 선택 모델에 맞는 ChatKHU, BizRouter 또는 DeepSeek API 키가 필요합니다.

- 프리셋: 빠른 초안, 다양한 초안, 정밀 생성, 형식 오류 수정. GPT·DeepSeek에 적용하며,
  미지원 모델은 기본 API 설정을 사용합니다. 최초 선택은 GPT-5.6 Luna와 정밀 생성입니다.
- 이번 실행의 모델·프리셋은 모든 유형에 동일하게 적용됩니다. 유형별 승인 기출,
  분석서, 프롬프트, 난이도와 소재 풀을 사용하며 기존 유형 설정은 바꾸지 않습니다.
- API 키, 승인 예시 또는 소재가 부족하면 실행 전 유형별 오류를 표시합니다.
  생성 시작 시 프롬프트와 설정을 고정하므로 재시도도 같은 설정을 사용합니다.
- 한 번에 한 작업을 백그라운드에서 실행합니다. 화면을 이동해도 계속 진행하며,
  텍스트 전용 작업은 서버 재시작 후 `실패·미완료 유형 재시도`로 재개합니다.
  미디어 자동 작업은 실행 중 서버가 종료되면 재시작 시 미완료 단계부터 자동 복구합니다.
  성공한 유형은 재호출하거나 중복 저장하지 않습니다.
- 기본 선택된 `음원·이미지 생성 및 DB 자동 등록`은 문항 생성 뒤 필수 미디어를 생성하고,
  S3·CloudFront 검증이 모두 끝나면 50문항과 미디어 주소·연결을 하나의 DB 트랜잭션으로 등록합니다.
  듣기는 시험 음원 35개 그룹을 50문항에 연결하고 그림 선택지 네 장을 준비합니다.
  도표는 구조화된 수치로 렌더링하며, 읽기 10번은 `visual_material.chart_spec`과 지문의 항목·수치가 일치해야 합니다.
- 50문항 저장이 완료되면 검수 완료(자동 승인)로 처리하고, 자동 등록 결과도 `reviewed`(승인)로 저장합니다.
  AI 검수·자동 수정은 실행하지 않습니다. 사람이 남긴 미승인 기록과 형식 오류는 기존 등록 검사에 반영합니다.
  문항을 수정했다면 아래의 미디어 완성 기능으로 변경분을 먼저 반영하세요.
- 미디어 자동 처리를 끄면 자동 승인된 텍스트 문항을 저장합니다. 기존 묶음은 이력의
  `선택 묶음 미디어 완성·자동 등록`으로 실행할 수 있으며 자동으로 유료 생성에 편입되지 않습니다.

생성 묶음과 고정 설정, 유형별 진행 상태는 `data/bulk_generation.db`에 기록하고,
문항은 기존 유형별 DB에 저장합니다. 전체 백업에는 작업 DB와 문항 연결 정보도 포함됩니다.

`생성 진행`에는 진행 중·미완료 작업을 표시합니다. PostgreSQL의 1~50번 문항과 필수 미디어 URL 연결이
완료된 묶음은 접힌 `완료된 생성 이력`에서 확인하며, 해당 영역의 등록·승인 확인 버튼으로 이동할 수 있습니다.
로컬에 오래된 중단·대기 기록이 남아 있어도 등록된 내용이 일치하면 완료 이력으로 분류합니다.
실행 중인 작업, 문항·미디어가 부족하거나 로컬 수정본이 있는 작업은 계속 진행 목록에 표시합니다.
검수 대기 여부는 완료 이력에 별도로 표시하고, 정리한 로컬 원본은 정리 이력으로 확인합니다.
등록 상태는 30초마다 읽기 전용으로 다시 조회하며 `등록 상태 새로 확인`으로 즉시 갱신할 수 있습니다.
DB 상태를 확인하지 못하면 작업을 숨기지 않습니다. 이 분류는 기록 삭제나 S3 파일 검증을 실행하지 않습니다.

### 음원·이미지 자동 처리 준비

`requirements.txt`를 설치하고 FFmpeg·FFprobe를 PATH에 준비합니다. 필요하면 `.env`의
`FFMPEG_PATH`, `FFPROBE_PATH`로 실행 파일을 지정합니다. Google 인증에는 ADC 또는
`GOOGLE_CLOUD_CREDENTIALS_JSON` 서비스 계정 JSON을 사용합니다. `.env.example`의
`GOOGLE_CLOUD_PROJECT_ID`, `GOOGLE_TTS_*`, `GOOGLE_IMAGE_*`와 기존 S3·CloudFront 설정을 확인하세요.
Google Cloud TTS·Vertex AI와 S3 접근 권한이 필요합니다. Google 음성·삽화 생성에는 해당 계정의 API 사용료가 발생합니다.

로컬 PostgreSQL은 기존 문항 버전 제거(006), 미디어(007), S3(008), 검수 대기(009) 마이그레이션이 필요합니다.
기존 DB를 백업한 뒤 `문제 등록·세트 만들기 → 고급 설정 · DB 연결·구조 관리 → DB 구조 준비`에서 적용합니다.
자동 처리 시작 전 인증·로컬 DB·버킷·실행 파일을 확인하며, 준비가 안 되어 있으면 모델 호출 전에 차단합니다.

TTS는 각 문장 요청 완료 후 기본 2초, 삽화는 기본 5초를 기다립니다. 화면에서 대기시간과 음성 속도를 조절할 수 있습니다.
429·일시적 5xx·연결 오류는 최대 5회 자동 재시도하며, 10·20·40·80·160초에 소량의 무작위 대기를 더합니다.
서버의 `Retry-After`가 더 길면 우선합니다. 인증·입력 오류는 반복하지 않습니다.

파일과 문장별 합성 결과는 `data/media_generation/`, 자산별 단계·재시도 기록은
`data/bulk_generation.db`의 `media_tasks`에 보존됩니다. 업로드만 실패하면 생성 결과를 재사용합니다.
한 건이라도 미완료면 최종 DB 등록을 보류하고 성공한 파일을 유지합니다. 실패 원인을 고친 뒤
`실패·미완료 유형 재시도`로 같은 설정을 재개하거나 미디어 완성 버튼으로 현재 설정을 새로 적용할 수 있습니다.

브라우저를 닫아도 Hub 서버가 실행 중이면 계속 처리합니다. 서버 재시작 시 자동 실행 중이던 작업은 재개합니다.
`현재 작업 중단`은 진행 중인 요청이 끝난 뒤 후속 처리를 중단합니다. 중단한 작업과 백업에서 복원한 작업은 자동 재개하지 않습니다.
백업에는 생성 파일도 포함됩니다. 이미 업로드한 S3 파일은 자동 삭제하지 않습니다.

### 문제 저장 현황

사이드바의 `문제 저장 현황`에서 SQLite 생성 문항·참고 예시 수, PostgreSQL 문항·세트·검수 상태를 확인합니다.
영역·모델·날짜로 필터링하고, 생성 묶음별 50문항 등록 수와 음원·이미지 준비 상태를 조회할 수 있습니다.
듣기는 음원 파일 수와 연결 문항 수를 구분합니다. 문항 상세에서는 양쪽 저장 내용, 검수 상태, 미디어 URL을 비교합니다.
검수 대기로 자동 등록된 문항도 정상적으로 집계하며, DB 연결 실패는 0건 대신 `확인 불가`로 표시합니다.

`현황 새로고침`으로 최신 기록을 읽습니다. SQLite는 읽기 전용 연결, PostgreSQL은 읽기 전용 트랜잭션을 사용하며,
이 화면에 진입하는 것만으로 스키마 변경·작업 자동 복구·S3 요청을 실행하지 않습니다. 이미 실행 중인 생성 작업은 계속됩니다.
작업 중에는 각 DB의 조회 시점 차이가 있을 수 있습니다. 미디어 준비 수량은 현재 문제에 대한 성공 작업 기록이며,
URL 등록 여부와 실제 파일 접근 여부는 별개입니다. `저장소·세트 → 선택 세트 S3·CloudFront 검증`을 누르면
선택한 세트의 실제 파일을 읽어 검증합니다. 검증 결과는 화면 세션에만 보관합니다.

### PostgreSQL 문제 관리

사이드바의 `PostgreSQL 문제 관리`에서 등록된 문제를 검색하고 직접 편집합니다.
로컬 SQLite 원본이 없어도 사용할 수 있으며, `문제 저장 현황`과 등록된 세트의 문항에서도 편집 화면을 열 수 있습니다.
세트 소속·문항 번호·유형·생성 출처는 고정하며 지문, 발문, 선지, 정답, 해설, 급수·난이도·평가 요소,
소재 정보, 듣기 대본과 도표 데이터를 수정할 수 있습니다. 선지 순서는 각 번호의 내용을 바꿔 편집합니다.

`변경 내용 확인`에서 영향받는 문항과 변경 전후 내용을 비교한 뒤 `PostgreSQL에 저장`을 누릅니다.
공통 지문·대본·듣기 반복 횟수는 같은 공통 문항에 함께 반영됩니다. 수정 후 문항과 세트는 검수 대기가 됩니다.
조회 이후 다른 작업이 문항·세트·미디어를 바꾸면 저장을 중단하므로 목록을 새로고침하고 다시 비교하세요.
PostgreSQL 편집본을 기존 `변경 내용 반영`으로 덮어쓰려면 별도 확인이 필요합니다.

음원은 MP3, 이미지는 PNG·WebP·JPEG 파일로 교체할 수 있습니다. 음원 검증에는 기존 ffmpeg·ffprobe 설정을 사용합니다.
문항 편집에서 직접 업로드하거나 재생성한 교체 파일은 S3의 `media/replacements/<파일 SHA-256>.mp3` 또는
`media/replacements/<파일 SHA-256>.png`에 저장합니다. 기존 파일과 주소는 유지합니다.
실제 저장을 실행할 때 S3 업로드와 CloudFront 파일 검증을 진행합니다. 변경되지 않은 미디어는 새 문항 내용에 다시 연결하고,
대본·발문·반복 횟수나 그림 자료가 바뀐 미디어는 교체 필요 상태로 처리합니다. 공유 음원 교체는 해당 문항 전체에 적용됩니다.
필수 미디어를 준비한 후 `문항 작업 → 검수 승인`으로 승인합니다. 수정 내용은 과거 버전으로 보관하지 않습니다.

`사용 중지`는 문항을 보관하는 논리 삭제이며 `사용 중지 문항 포함`으로 조회하고 검수 대기로 복원할 수 있습니다.
`영구 삭제`는 별도 확인 후 문항과 해당 미디어 연결을 삭제합니다. 참조하는 사용 기록이 있으면 삭제를 차단합니다.
세트의 다른 문항 번호는 유지하며, 삭제된 문항이 있는 세트는 `49/50 · 구성 미완성 · 사용 불가`처럼 표시합니다.
S3 파일과 로컬 생성 기록은 삭제하지 않습니다. 업로드 이후 DB 저장이 실패한 경우에도 업로드 파일은 S3에 남습니다.
새 HTTP API, DB 테이블, 마이그레이션 또는 백그라운드 작업은 추가하지 않습니다.

## 코드 구조와 생성 순서

실행 시작점은 `topik_question_lab/main.py`이며, 단계별 코드는 다음 폴더에 있습니다.

| 순서 | 폴더 | 역할 |
| --- | --- | --- |
| 1 | `step_01_source/` | 읽기 기출 파싱과 듣기 자료 가져오기 |
| 2 | `step_02_planning/` | 유형 규칙, 소재 선정과 프롬프트 구성 |
| 3 | `step_03_generation/` | 모델 호출, 생성 결과 처리와 50문항 일괄 생성 |
| 4 | `step_04_review/` | 응답·문항 검증과 밑줄 표시 |
| 5 | `step_05_export/` | JSON·CSV·TXT·PDF 내보내기 |
| 6 | `step_06_publication/` | 세트 구성, PostgreSQL 등록과 미디어 검증 |

모든 폴더는 `topik_question_lab/` 아래에 있습니다. `common/`은 모델·SQLite 저장·시각 자료,
`ui/`는 Streamlit 화면과 화면 보조 코드, `maintenance/`는 백업·로컬 서버 관리를 담당합니다.
SQL 마이그레이션과 AWS 정의는 `step_06_publication/migrations/`,
`step_06_publication/cloudformation/`에 있습니다.
데이터 경로는 프로젝트 루트의 `data/`를 사용합니다.

## 작업 흐름

1. 사이드바에서 실험할 문제 유형을 선택합니다.
2. `기출 데이터`에서 해당 유형의 원문, 지문과 보기 4개를 검토합니다.
3. 정답, 출제 포인트와 설명이 비어 있으면 `AI로 누락 정보 보완`을 실행하거나 직접 입력합니다.
4. 검토가 끝난 문제만 `학습 예시로 승인`합니다.
5. `유형 분석`에서 모델별 분석을 비교하고 공통 유형 분석서를 편집합니다.
6. `프롬프트 작업실`에서 생성 수, 난이도, 공통/모델별 지침, 모델별 생성 프리셋과 최종 프롬프트를 확인합니다.
7. `문제 생성`에서 ChatKHU 웹 응답을 붙여넣거나 Gateway 모델을 선택해 실행합니다.
8. `검수·비교`에서 생성 문제를 수정하고 점수와 승인 여부를 저장합니다.
9. `내보내기`에서 승인 문제를 TXT, JSON 또는 CSV로 저장합니다.
10. 두 모델의 결과를 직접 비교하려면 `원본 · 모델 A · 모델 B 비교 PDF`에서 실제 사용 모델 두 개와 포함 범위를 선택해 PDF를 받습니다.
11. `문제 등록·세트 만들기`에서 대상 선택 → 내용 확인 → 등록 완료 순서로 문제 또는 50문항 세트를 저장합니다.

`기출 데이터`의 `저장하고 다음 문제`와 `검수·비교`의 `평가 저장하고 다음 문제`는 저장 성공 후 다음 항목으로 이동합니다. 마지막 문제에서는 현재 위치를 유지합니다.

`AI로 누락 정보 보완`에서는 보완 대상 문제를 회차·번호·질문 문구별로 선택할 수 있습니다. 선택한 문항만 API 및 복사 가능한 프롬프트에 포함되며, 응답에 선택하지 않은 문항이 들어 있어도 해당 문항에는 적용하지 않습니다.

## 원문 추가

### 추출된 텍스트 추가

`extracted_text`에 `*_questions.txt` 파일을 추가한 뒤 앱에서 `기출 데이터 > 텍스트 다시 스캔`을 누릅니다. 보기 번호 순서가 섞여 있어도 번호를 기준으로 정규화합니다.

### HTML 추가

새 HTML 파일을 `html변환` 폴더에 넣은 뒤 `기출 데이터 > HTML 변환 후 스캔`을 누릅니다.

원문 파일은 앱에서 수정하거나 삭제하지 않습니다.

## 지원 문제 유형

| 문제 번호 | 유형 |
|---|---|
| 1~2 | 문법 빈칸 |
| 3~4 | 유사 표현 |
| 5~8 | 짧은 글 소재 |
| 9~12 | 안내문·도표 내용 일치 |
| 13~15 | 문장 순서 |
| 16~18 | 짧은 글 빈칸 |
| 19~20 | 공통 지문: 빈칸·주제 |
| 21~22 | 공통 지문: 표현·내용 |
| 23~24 | 서사 지문: 심정·내용 |
| 25~27 | 신문 제목 해석 |
| 28~31 | 긴 글 빈칸 |
| 32~34 | 긴 글 내용 일치 |
| 35~38 | 글의 주제 |
| 39~41 | 문장 삽입 |
| 42~43 | 문학 지문: 심정·내용 |
| 44~45 | 논설 지문: 빈칸·주제 |
| 46~47 | 논설 지문: 태도·내용 |
| 48~50 | 고급 지문: 목적·빈칸·내용 |

공통 지문 문제는 세트 ID로 묶입니다. 한 문제의 공통 지문을 수정하면 같은 기출 세트 또는 모델 실행 세트의 지문도 함께 갱신됩니다.

44~45번은 회차에 따라 출제 순서가 다릅니다. 47~64회는 `44번 주제 · 45번 빈칸`, 83회 이후는 `44번 빈칸 · 45번 주제`이며, 앱은 질문 문구로 역할을 판별해 실제 번호와 순서를 보존합니다. 새 문제는 현행 순서로 생성합니다.

23번과 42번처럼 밑줄 위치가 텍스트 추출 결과에 남지 않는 문항은 기출 검토 화면의 지문에서 대상 부분을 `[[이렇게]]` 감싸거나 `밑줄 대상 표현` 입력란에 직접 입력해 지정할 수 있습니다. 밑줄이 지정되지 않은 문항은 AI 보완 대상에서 제외되어 먼저 수동 확인할 수 있습니다.

PDF/HTML 변환 과정에서 보기나 도표 구조가 사라진 문제는 버리지 않고 `구조 확인 필요` 상태로 가져옵니다. 문장 삽입 유형은 `주어진 문장`과 `(①)~(④)` 위치를 별도 필드로 관리합니다.

## 데이터 저장

유형별 DB는 다음 위치에 저장됩니다.

```text
data/types/<question_type>.db
```

각 DB에는 다음 데이터가 들어 있습니다.

- 정규화된 기출과 승인 상태
- 유형 분석서와 프롬프트 버전
- 모델 ID, 실제 요청 프롬프트와 원본 응답
- 유형·모델별 생성 프리셋과 실제 적용된 비밀값 없는 API 파라미터
- 토큰 사용량, 실행 시간과 오류
- 생성 문제, 자동 검사와 사람 평가

### 생성 묶음 등록·승인

`50문제 일괄 생성` 화면의 **이 묶음 등록·승인 확인**으로 통합 등록 화면에 이동합니다.
새로 자동 등록된 묶음은 이미 승인 상태입니다. 이전 검수 대기 묶음은 승인 후
**생성 묶음 내용 확인 → 선택 세트 승인 상태 반영**으로 처리할 수 있습니다.
텍스트만 생성한 묶음도 자동 승인되며 같은 흐름에서 50문제 세트로 등록할 수 있습니다. 미디어 준비 상태는 별도로 표시합니다.

프로젝트 루트 `.env`에는 로컬 PostgreSQL 연결을 설정합니다.

```dotenv
DATABASE_URL=postgresql://user:password@localhost:5432/topik
```

- 등록은 `DATABASE_URL`만 사용합니다. 이전 원격 DB 연결 설정은 사용하지 않습니다.
- 등록 전 기존 스키마와 제약을 읽기 전용으로 확인합니다. 처음 사용하는 DB는 고급 설정에서 스키마를 준비하세요.
- 미승인·누락·중복·현재 편집본 오류·공통 지문 불일치는 등록 전에 차단합니다.
- 검증한 내용과 대상 DB는 `data/publication_jobs.db`에 고정됩니다. 문항·승인·설정이 바뀌면 다시 검증해야 합니다.
- 선택한 세트는 하나의 트랜잭션으로 등록합니다. 같은 내용의 재시도는 기존 세트를 재사용하며, 다른 내용은 충돌로 차단합니다.
- 등록 후 새 연결로 실제 조회 뷰의 50문항 내용과 순서를 확인합니다.
- 등록 이력에서 **등록 결과 다시 확인** 또는 **같은 작업 재시도**를 사용할 수 있습니다.
- 이전 DB 대상의 등록 기록은 **이전 DB · 조회 전용**으로 표시하며, 이전 DB에 접속하지 않습니다.
- 등록 작업은 SQLite 백업·복원에 포함됩니다. PostgreSQL과 미디어 파일은 별도로 백업하세요.

### 문제 등록·세트 만들기

사이드바의 `문제 등록·세트 만들기`에서 **대상 선택 → 내용 확인 → 등록 완료** 순서로 진행합니다.
DB 연결은 읽기 전용으로 확인하므로 매번 연결 준비나 스키마 적용 버튼을 누를 필요가 없습니다.

- **문제 추가하기**: 승인·자동검사를 통과한 미등록 문제를 선택하고, `선택 내용 확인` 후 `선택한 N문제 등록하기`를 누릅니다.
- **50문제 세트 만들기**: 영역·모델·생성 출처를 선택합니다. 기존 개별 문제는 미사용 후보로 1~50번을 구성하며,
  복수 후보는 최신순으로 미리 선택됩니다. 확인 후 세트 등록 버튼을 누르면 문항도 함께 저장합니다.
- **변경 내용 반영**: 상단 `저장 내용 비교 필요 보기`에서 대상 문제를 선택하고 양쪽 내용을 비교한 뒤 반영합니다.
  기존 문제는 기본으로 선택되지 않으며, 확인한 대상 외의 문제를 덮어쓰지 않습니다.
- **생성 묶음 등록·승인**: 자동 승인·등록된 묶음의 상태를 확인합니다. 이전 검수 대기 묶음은 승인 후 같은 세트의 승인 상태만 반영할 수 있습니다.
  미완성 미디어는 `50문제 일괄 생성`의 기존 재시도 기능을 사용합니다.
- **등록된 세트**: 문제·음원 연결·이미지 수와 검수 상태를 확인합니다. 음원 파일 수와 연결 문항 수를 구분하며,
  실제 S3·CloudFront 파일 검증은 `음원·이미지 실제 파일 확인`을 눌렀을 때만 실행합니다.

급수·난이도·출제 능력은 `세부 설정`에서 조정합니다. 기존 문제는 저장된 설정을 우선 사용하고,
새 문제는 기본 TOPIK 4급·예상 난이도 0.0을 사용합니다. 문항 수동 등록으로 유료 미디어 생성을 시작하지 않습니다.
등록 완료와 미디어 준비 완료는 별개이며, 미디어가 부족한 세트에는 필요한 문항 번호를 표시합니다.
등록된 듣기 문제의 내용·설정이 변경되면 해당 공유 음원 연결을 준비 필요 상태로 돌립니다.
기존 음원 파일은 삭제하지 않으며, 승인 상태만 반영할 때는 미디어 연결을 유지합니다.

확인 후 문제·승인·DB 내용이 바뀌면 다시 선택해야 합니다. 등록 응답이 끊겼을 때는 `최근 등록 결과`에서
`등록 결과 다시 확인`을 먼저 실행하고, 미반영으로 확인된 작업만 같은 작업으로 재시도합니다.
작업 이력은 기존 `data/publication_jobs.db`를 사용합니다. 조회·필터 조작만으로 DB 파일을 만들거나 구조를 변경하지 않습니다.

#### 등록 완료 세트 로컬 정리

`문제 등록·세트 만들기 → 등록 완료 세트 로컬 정리`에서 대상 세트를 여러 개 선택하고
`선택 세트 정리 내용 확인`을 누릅니다. 삭제할 수량과 대상을 확인한 뒤 체크박스를 선택하고
`백업 후 N문제 로컬 정리하기`를 눌러야 실제 데이터가 변경됩니다. 조회·선택만으로는 정리하지 않습니다.

PostgreSQL의 1~50번 문항·세트가 승인 상태이고, 남아 있는 로컬 문제도 승인되었으며,
필수 음원·이미지의 S3 등록 정보와 URL 연결이 모두 갖춰진 세트만 정리합니다.
텍스트 생성이 미완료이거나 미디어 단계가 실행·대기 중이면 차단합니다. PostgreSQL 승인·문항·필수 미디어 등록을
확인한 세트는 로컬의 오래된 중단·실패 기록만으로 정리를 막지 않습니다. 실행 잠금으로 실제 실행 중인 작업과의 충돌을 방지합니다.
실제 S3 파일 접근 검증은 별도이며 정리 과정에서는 S3에 요청하지 않습니다.

실행 직전에 상태를 다시 확인하고, `backups/before_set_cleanup_<고유 ID>.zip`에 전체 로컬 기록 백업을 저장한 뒤
저장된 ZIP의 무결성을 확인합니다. 백업 실패 시 문제를 삭제하지 않습니다.
선택한 세트의 SQLite 문제와 검수 기록만 삭제하며, PostgreSQL·S3와 생성·등록 이력은 유지합니다.
로컬과 PostgreSQL 내용이 다르더라도 PostgreSQL을 기준으로 유지하고 로컬 내용은 백업에서 복구할 수 있습니다.
휴지통 복원이 아닌 기존 백업 복원 절차를 사용합니다.

기존 유형별 SQLite `settings`에 세트 ID·DB 대상 식별값·문제 식별값·정리 시각·백업 경로를 기록합니다.
새 API·테이블·스키마 변경은 없습니다. 정리한 묶음은 재생성·미디어 자동 등록 재실행을 차단합니다.
SQLite 파일별로 트랜잭션을 적용하므로 일부 파일 저장 실패 시 확인된 정리 수량과 백업 경로를 표시합니다.
새로고침 후 남은 문제를 다시 선택해 이어서 정리할 수 있습니다.

#### 미등록 문제 정리와 휴지통

`문제 등록·세트 만들기 → 미등록 문제 정리`에서 영역·모델로 목록을 좁히고 여러 문제를 선택한 뒤
`선택한 N문제 휴지통으로 이동`을 누릅니다. 승인하지 않은 문제도 정리할 수 있습니다.
휴지통 문제는 등록 후보·검수 목록·세트 구성과 활성 문항 집계에서 제외하며, 문제 내용·ID·기존 승인 및 실행 기록은 보존합니다.

`휴지통 보기`에서 문제를 여러 개 선택하고 `선택한 N문제 복원하기`를 누르면 원래 상태로 복원합니다.
복원은 PostgreSQL 등록이나 새 검수 승인을 실행하지 않습니다. 영구 삭제 기능은 제공하지 않습니다.
등록된 문제와 일괄 생성 묶음·생성 영수증에 연결된 문제는 개별 처리를 제한합니다.
DB 연결이 없거나 등록 여부를 확인할 수 없으면 휴지통 이동·복원을 실행하지 않습니다.

휴지통 상태는 기존 유형별 SQLite의 `generated_questions.trashed_at`에 저장합니다.
이 컬럼은 실제 이동을 실행한 DB에만 추가되며, 기존 DB를 조회하는 것만으로는 추가하지 않습니다.
여러 DB의 대상은 먼저 모두 검사하고 DB별 트랜잭션으로 저장합니다. 저장 중 오류가 발생하면 확인된 처리 수를 표시하므로
새로고침 후 남은 항목을 확인하세요. 전체 SQLite 백업·복원에는 휴지통 상태도 함께 포함됩니다.

최초 DB 설정은 `고급 설정 · DB 연결·구조 관리`에서 수행합니다. 기존 DB는 전체 백업 후 구조 준비를 실행하세요.
스키마와 조회 SQL은 [문항 은행 문서](POSTGRESQL_QUESTION_BANK.md), 파일 검증 조건은
[로컬 미디어 검증 안내](docs/LOCAL_MEDIA_DEPLOYMENT.md)를 참고하세요.

Hub는 `DATABASE_URL`에 설정한 로컬 문항은행을 사용합니다.
`manage_bank_server.ps1`로 기존 5434 Bank 서버를 시작·중지하거나 상태를 확인할 수 있습니다.
자세한 사용법은 [로컬 Bank 서버 안내](docs/LOCAL_BANK_SERVER.md)를 참고하세요.

최초 발행 문항은 `reviewed` 상태입니다. 동일한
문항 내용을 다시 동기화하면 기존 행을 재사용하고, 문항 내용이나 메타데이터가 바뀌면
같은 `item_id`의 현재 내용을 갱신합니다. 문항 버전 번호와 수정 이력은 저장하지 않으며,
이미 구성한 세트에도 갱신된 문항 내용이 반영됩니다. 한 번이라도 PostgreSQL 세트에 포함된 `source_key`는 이후
새 세트 후보에서 제외됩니다. 같은 모델·영역의 미사용 1~50번이 다시 완성되면 기존 세트를
교체하지 않고 자동 증가하는 세트 번호와 별도 `set_id`로 발행합니다. 듣기 그림·그래프는
설명, 생성 프롬프트와 상대 경로만 저장하며 이미지 바이너리는 저장하지 않습니다.

PostgreSQL 연결이 없거나 실패해도 기존 생성·검수·파일 내보내기 기능에는 영향을
주지 않습니다. 연결 문자열과 비밀번호는 UI, SQLite DB 및 발행 데이터에 저장되지
않습니다. 배포 이력에는 비밀번호 없는 대상 호스트/DB 표시와 연결 식별 해시만 남습니다.

등록한 문항과 세트의 현재 내용은 다음 PostgreSQL 뷰로 조회합니다.

```sql
-- 문항별 현재 내용
SELECT *
FROM topik_bank.current_items
WHERE review_status IN ('reviewed', 'pilot', 'active');

-- 지정 세트의 1~50번 현재 내용
SELECT *
FROM topik_bank.current_set_contents
WHERE set_id = '세트 UUID'
ORDER BY position;
```

`current_items`에는 지문·대본, 보기, 정답, 해설, 전체 `content_json`, 생성 모델과
로컬 `source_key`가 포함됩니다. `current_set_contents`는 `items.set_id`와 `items.position`으로
구성한 세트의 현재 문항 내용을 반환합니다. 문제 은행의 핵심 테이블은 `items`, `question_sets` 두 개이며,
생성·검수·프롬프트·소재·일괄 작업·등록·배포 이력을 위한 보조 저장소는 유지합니다.
기존 DB는 이관 전에 백업하세요. 세트에 소속된 문항은 기존 세트가 사용하던 내용을 보존하고,
미배정 문항은 최신 내용만 남깁니다. 여러 세트에 연결된 문항이나 외부 참조가 있으면 이관이 중단됩니다.

사이드바의 `유형 DB 관리`에서 DB를 삭제할 수 있습니다. 유형 ID 재입력과 확인 체크를 모두 통과해야 삭제가 실행됩니다. `extracted_text` 원문은 유지되며, 삭제한 유형을 다시 열면 새 DB를 만들고 원문을 다시 수집합니다.

## 프롬프트 모드

- `공통 프롬프트`: 모든 모델에 같은 지시문을 전달해 성능을 같은 조건에서 비교합니다.
- `모델별 최적화`: 공통 규칙에 모델별 짧은 실행 지침을 추가합니다.

모델별 지침은 `프롬프트 작업실`에서 편집할 수 있습니다. 실제 실행에 사용된 전체 프롬프트는 실행 기록에 보존됩니다.

## 모델별 문제 생성 프리셋

프리셋은 읽기와 듣기의 `프롬프트 작업실`에서만 변경하며 **문제 생성 API 호출에만** 적용합니다. 유형 분석, 정답·해설 보완, 이미지 전사는 기존 기본 요청을 유지합니다. 설정은 각 유형 SQLite DB의 `settings` 테이블에서 `generation_presets` 키의 JSON 맵으로 저장되므로 읽기·듣기, 문제 유형, 모델마다 선택을 독립적으로 기억합니다. 저장된 값이 없거나 유효하지 않으면 `정밀 생성`을 사용합니다.

| 프리셋 | DeepSeek | GPT/ChatKHU | 목적 |
| --- | --- | --- | --- |
| 빠른 초안 | thinking 끔, `temperature=0.3` | `reasoning_effort=low` | 수량·스키마·정답 유일성을 지키며 빠르게 생성 |
| 다양한 초안 | thinking 끔, `temperature=0.75` | `reasoning_effort=low` | 소재·상황·인물 다양화 |
| 정밀 생성 | thinking 켬, `reasoning_effort=high` | `reasoning_effort=high` | 정답·오답·TOPIK 적합성 최종 검토 |
| 형식 오류 수정 | thinking 끔, `temperature=0.1` | `reasoning_effort=low` | 설명·코드펜스 없이 JSON 구조 복구 |

모든 지원 프리셋은 JSON object 응답 형식과 32,768토큰 출력 한도를 사용합니다. DeepSeek는 `max_tokens`, GPT는 `max_completion_tokens`를 전송합니다. GPT에는 호환성 문제를 피하기 위해 `temperature`와 `top_p`를 보내지 않으며, DeepSeek thinking 모드에도 효과가 없는 두 값을 보내지 않습니다. DeepSeek 모델과 모델 ID가 `gpt-`로 시작하는 모델만 지원하며 Claude·Gemini·EXAONE 등은 UI에 `프리셋 미지원 · 기본 API 설정`으로 표시되고 기존 payload를 그대로 사용합니다.

프리셋 지침은 실제 시스템 프롬프트에도 추가되므로 `runs.prompt_system`과 PostgreSQL `prompt_version`이 실행 내용을 반영합니다. API 실행의 `ProviderResult.request_parameters`에는 실제로 보낸 비밀값 없는 설정과 `api_parameters_applied=true`가 기록됩니다. 웹 수동 생성은 복사용 프롬프트에 지침만 포함하고 `api_parameters_applied=false`로 기록합니다. API 키는 `.env`에서만 읽으며 SQLite나 PostgreSQL에 저장하지 않습니다.

## 공용 소재 은행과 다양화 생성

읽기와 듣기의 문제 생성 단계는 `data/topic_bank.db`의 공용 소재 은행을 사용합니다. 최초 실행 시
12개 분야, 120개 소재와 소재별 접근 관점 3개가 자동으로 등록됩니다. 사이드바의 `소재 은행`에서
소재를 검색하고 추가·수정하거나 생성 후보에서 비활성화할 수 있습니다.

문제 생성 화면에서는 독립 문항당 하나, 공통 지문·대본 세트당 하나의 소재를 모델별로 자동
배정합니다. 최근 읽기·듣기 전체에서 사용한 50개 소재·관점 조합은 제외되며, 분야와 과거 사용
횟수를 고려해 적게 사용된 소재가 우선됩니다. 배정표는 생성 전에 확인할 수 있고 선택 항목 또는
전체를 다시 추첨할 수 있습니다. 실제 모델 프롬프트에는 전체 은행이 아니라 선택된 소재만
포함되며, 성공적으로 저장된 생성 결과부터 사용 이력에 기록됩니다.

`소재 은행 > 문항별 지정 풀`에서는 읽기·듣기 영역과 적용 번호를 직접 지정하고 소재 목록과
프롬프트 지침을 일괄 편집할 수 있습니다. 읽기 5·6·7·8·11~12·25~27·44~50번과 듣기
41~50번 풀은 기본값으로 제공됩니다. 지정 풀이 있는 번호는 공용 소재보다 우선하며, 앱이 풀에서
한 항목만 골라 모델에 전달합니다. 항목은 사용 횟수가 적은 것부터 순환하므로 전체를 사용하기
전에는 가능한 한 반복되지 않습니다. 풀을 비활성화하면 해당 번호는 기존 공용 소재 방식으로
돌아가며 사용 이력은 유지됩니다.

읽기 1~4번 문법·유사 표현과 듣기 1~20번의 짧은 문항은 사용자 지정 풀이 없으면 별도의 지문
소재 배정을 생략합니다. 사용자가 이 번호에 직접 풀을 등록하면 명시적 설정을 우선 적용합니다.
그 밖의 유형은 짧은 안내문, 서사, 일반 설명, 전문 대화·강연의 성격에 맞춰 공용 소재 범위를
다르게 적용합니다.

기존 생성 문항은 자동 분류하거나 변경하지 않습니다. 신규 문항에는 `topic_id`, `topic_domain`,
`topic_title`, `topic_angle`이 저장되고 검수 화면에서 소재 준수도를 함께 평가할 수 있습니다.
소재 DB와 사용 이력은 전체 백업·복원에 포함됩니다.

## TOPIK II 단어장 등록

사이드바의 `TOPIK II 단어장` 메뉴에서 전체 또는 3~6급 단어를 조회할 수 있습니다.
검색어는 한국어 단어, 영어·베트남어·일본어·중국어(간체)·인도네시아어 뜻, 한·영 예문에서
부분 검색하며 영문 대소문자를 구분하지 않습니다. 목록은 급수·단어 순으로 50개씩 표시하고 `이전`·`다음`
버튼 또는 페이지 번호로 이동합니다. 급수나 검색어를 바꾸면 첫 페이지로 돌아갑니다.
`상세 보기`에서 현재 페이지의 단어를 선택하면 다국어 뜻과 한·영 예문을 확인할 수
있습니다. 상단 급수별 건수는 전체 단어장 기준이고 검색 결과 수는 현재 필터 기준입니다.
`새로고침`으로 최신 등록 내용을 조회합니다. 조회만으로는 데이터를 변경하지 않습니다.

중국어(간체)·인도네시아어 뜻은 8,258개 단어 전체에 대해 작성한 정적 CSV 데이터입니다.
조회·검색·등록 중 번역 AI API를 호출하지 않습니다. 아직 뜻 열을 추가하지 않은 DB도
조회할 수 있으며, 새 언어의 빈 뜻은 `미등록`으로 표시합니다.

### 단어 음성 생성·재생

`TOPIK 단어장 > TOPIK II 단어장`의 단어 상세 아래에서 음성을 생성하고 재생합니다.
처음에는 `음성 기능 준비`를 눌러 단어장 JSON 백업 후 `014_vocabulary_audio`를 적용합니다.
기존 `topik_bank.vocabulary`에 음성 저장 정보 8개 컬럼을 추가하며, 새 테이블·HTTP API·
백그라운드 워커는 만들지 않습니다. 단어·뜻·예문·ID는 그대로 유지합니다.

기존 Google TTS 인증과 `GOOGLE_CLOUD_PROJECT_ID`, `S3_BUCKET`, `CLOUDFRONT_BASE_URL`,
AWS 인증, FFmpeg·FFprobe 설정을 사용합니다. `음성 생성 설정`에서 화자와 낭독 속도를
선택하고 `선택 단어 음성 생성` 또는 `선택 단어 음성 재생성`을 누릅니다. 한국어 표제어만
한 번 낭독하며 번역이나 예문을 읽지 않습니다. 먼저 소수의 단어로 발음을 확인하세요.
단어장 전용 지침은 표준 한국어, 중립적인 사전 낭독, 작은 억양·강세, 고른 속도를 지정합니다.
실제로 전송한 지침과 버전은 음성 생성 설정에 함께 저장하며, 이전 지침으로 생성한 음성은
갱신 대상으로 표시합니다. 문제 듣기 음성의 기존 낭독 지침은 유지합니다.

`음성 일괄 생성`은 현재 급수·검색어 범위의 **음성 없는 단어** 또는 **갱신 필요한 단어**를
한 번에 1~100개(기본 20개) 처리합니다. 실행 중에는 화면을 유지하세요. 완료된 단어는
즉시 저장되어 다음 실행에서 제외되며, 실패한 단어의 파일은 `data/vocabulary_audio/`에
보관해 재시도에 사용합니다. 처리 결과와 실패 항목은 화면에 표시됩니다.

파일은 `media/vocabulary-audio/<파일 SHA-256>.mp3` 경로로 S3에 저장합니다. S3 파일과
CloudFront 재생 응답을 검증한 뒤 DB 연결을 교체하므로 검증 실패 시 기존 음성은 유지됩니다.
이전 S3 파일을 자동 삭제하지 않습니다. 단어 낭독문·모델·화자·속도가 달라지면 갱신 대상으로
표시하며 뜻·예문·급수 변경만으로는 재생성하지 않습니다. 목록의 음성 필터로 등록 여부를
확인할 수 있고 상세 화면에서 CloudFront 음성을 재생합니다.

`TOPIK-II-Word/topik-2-all.csv`를 `.env`의 `DATABASE_URL`이 가리키는 관리 대상 로컬
PostgreSQL에 등록합니다. 기존 Python 의존성을 사용합니다.

```powershell
.\.venv\Scripts\python.exe -m topik_question_lab.maintenance.import_vocabulary --check-only
.\.venv\Scripts\python.exe -m topik_question_lab.maintenance.import_vocabulary
```

다른 CSV는 `--csv 경로`로 지정합니다. `--check-only`는 DB에 접속하지 않습니다.
등록 명령은 전체 CSV를 검증하고 `backups/postgres/`에 DB 백업을 만든 뒤,
필요한 `012_vocabulary`와 `015_vocabulary_languages` SQL 및 데이터 등록을 한 트랜잭션으로
적용합니다. 중국어·인도네시아어 열을 포함한 CSV를 등록할 때 015를 적용합니다.
기존 DB에서 앱을 실행하기 전에 이 명령을 실행하세요. 이미 있는 열은 유지합니다.

단어장은 `topik_bank.vocabulary`를 사용하며, 언어 확장은 이 테이블에 두 뜻 열만 추가합니다.
언어 확장으로 새 테이블이나 HTTP API를 추가하지 않습니다.
`vocabulary_id`는 자동 생성되는 기본 키이고 CSV 열은 다음과 같이 저장됩니다.

| CSV 열 | DB 열 |
| --- | --- |
| Korean | `korean` |
| Part of speech | `part_of_speech` |
| English / Vietnamese / Japanese | `english` / `vietnamese` / `japanese` |
| Example (Korean) / Example (English) | `example_korean` / `example_english` |
| TOPIK level | `topik_level` (3~6) |
| Chinese (Simplified) | `chinese_simplified` |
| Indonesian | `indonesian` |

UTF-8(BOM 포함 가능) CSV는 기존 8개 열 또는 위 순서의 10개 열을 받습니다.
품사와 새 언어 뜻은 빈 문자열을 허용하고 나머지 열은 필수입니다. 기존 8열 CSV나
새 언어 뜻이 빈 CSV를 가져와도 이미 저장된 중국어·인도네시아어 뜻을 지우지 않습니다.
원문은 그대로 보존하며 급수만 정수로 저장합니다.
같은 한국어·품사는 기존 ID를 유지하며 뜻·예문·급수를 갱신합니다. CSV 내부의 중복
단어·품사는 오류로 처리하고, CSV에 없는 기존 단어는 삭제하지 않습니다.
등록 시 전체 저장 내용을 검증하고 커밋 후 별도 연결에서 CSV 전체를 다시 대조합니다.
결과에는 신규·수정·동일 건수, CSV 급수별 건수와 백업 경로가 표시됩니다.

```sql
SELECT topik_level, count(*) FROM topik_bank.vocabulary GROUP BY topik_level ORDER BY topik_level;
```

### 로컬·운영 서버에 단어장 등록

`TOPIK 단어장 > 서버에 단어장 등록`에서 로컬 서버, 운영 서버 또는 둘 다 선택한 뒤
`등록 내용 확인` → `선택 서버에 단어장 등록` 순서로 실행합니다. 원본은 `DATABASE_URL`,
대상은 기존 `QUESTION_BANK_LOCAL_DATABASE_URL` / `QUESTION_BANK_PRODUCTION_DATABASE_URL`을
사용합니다. 미리보기는 읽기 전용이며 원본·대상의 급수별 건수와 신규·변경·동일·충돌·대상
전용 건수를 보여줍니다. 대상 테이블이 없으면 등록 실행 시 `topik_bank.vocabulary` 하나만
동일한 구조로 생성합니다. 새 HTTP API·작업 이력 테이블·백그라운드 작업은 추가하지 않습니다.

전체 3~6급 단어의 원본 ID와 기존 8개 데이터 열, 준비된 중국어(간체)·인도네시아어 뜻 및
음성 메타데이터를 복사합니다. 새 언어 열이 없는 대상은 미리보기에 구조 갱신을 표시하고
등록 시 백업 후 두 열을 추가합니다. 원본의 새 언어 뜻이 비어 있으면 대상의 기존 뜻을
보존합니다. 새 언어 열이 있는 대상으로 전송하려면 원본에도 해당 열을 먼저 준비해야 합니다.
음성 컬럼이 없는 대상은 미리보기에 구조 갱신을 표시하고, 등록 시 백업 후 컬럼을 추가합니다.
음성 파일은 같은 S3 저장소를 공유하며 대상 서버에서도 해당 CloudFront에 접근할 수 있어야 합니다.
음성 컬럼이 있는 대상으로 전송하려면 원본에도 음성 기능을 먼저 준비해야 합니다.
원본에 음성이 없는 단어는 대상의 기존 음성 연결을 보존합니다. 음성 신규·변경·보존 건수는
등록 미리보기에 표시하며 S3 파일 자체는 삭제하지 않습니다.
ID·단어·품사가 모두 같은
행의 뜻·예문·급수는 갱신하고, 대상에만 있는 단어는 보존합니다. 같은 ID의 단어·품사가 다르거나
같은 단어·품사의 ID가 다르면 중단합니다. 원본 DB로의 전송, 중복 대상 선택, 호환되지 않는
컬럼·제약·인덱스·자동 증가 구조, 행 보안 또는 사용자 트리거가 있는 테이블도 차단합니다.

미리보기 이후 원본·대상 데이터나 구조가 바뀌면 다시 확인해야 합니다. 변경할 기존 대상
단어장은 `backups/vocabulary/before_transfer_*.json`에 구조·전체 행·자동 증가 상태와 검증
해시를 먼저 저장합니다. 백업에는 연결 문자열이나 비밀번호가 포함되지 않습니다. 이 파일은
단어장 전용 JSON 백업이며 `pg_restore`용 덤프가 아닙니다. 현재 동일한 데이터와 정상 자동
증가 상태는 변경하지 않으므로 반복 실행 시 불필요한 백업을 만들지 않습니다.

서버마다 테이블 생성·추가·갱신·자동 증가 번호 보정을 한 트랜잭션으로 실행합니다.
커밋 전에 전체 내용과 대상 전용 단어 보존을 검증하고 커밋 후 별도 연결에서 재확인합니다.
커밋 응답이나 최종 조회가 끊기면 성공으로 간주하지 않고 결과 확인 필요로 표시합니다.
두 서버 중 하나가 실패해도 다른 서버의 성공은 유지하며, 실패한 서버만 선택해 미리보기부터
재시도할 수 있습니다. 결과의 원본 건수·급수별 검증은 원본 등록분 기준이며 대상 전체 건수에는
대상에만 있던 단어도 포함됩니다.

## 50문항 생성 완료 시 자동 승인

`50문제 일괄 생성`에서 읽기·듣기 1~50번이 모두 정상 생성·저장되면 기존 검수 기록에
승인을 저장합니다. AI 검수·자동 수정과 별도의 검수 모델 사전 확인은 실행하지 않습니다.
문항 수·번호·공통 지문·대본 등 기존 형식 검사는 유지하며, 일부 유형이 실패하면 전체
묶음이 완성될 때까지 자동 승인하지 않습니다. 사람이 남긴 승인·미승인 기록은 덮어쓰지 않습니다.

`음원·이미지 생성 및 DB 자동 등록`을 선택하면 승인 후 필수 미디어를 준비·검증하고
로컬 PostgreSQL에 승인 상태로 등록합니다. 선택하지 않으면 승인된 로컬 문항을 저장하고,
나중에 `선택 묶음 미디어 완성·자동 등록` 또는 등록 화면에서 이어서 처리할 수 있습니다.
형식 오류나 필수 미디어 누락이 있으면 DB 등록은 보류됩니다.

이전 AI 검수 실행 기록과 유효한 승인 이력은 보존합니다. 중단된 이전 묶음을 재개해도
AI 검수·수정 호출 없이 문항 생성·자동 승인·미디어 처리 순서로 진행합니다.
신규 HTTP API·DB 테이블·스키마 변경은 없습니다.

## 단어별 연습문제 생성

사이드바의 `TOPIK 단어장 > 단어 연습문제 생성`에서 선택 단어 또는 검색 결과를 생성 대상으로 지정합니다.
기본 선택 모델은 BizRouter의 `gpt-6-luna`입니다.
빈칸 3문항은 객관식·주관식으로 표시할 수 있으며, 동사·형용사는 활용형 3문항을 추가합니다.
문맥상 적절한 경우 유의어 또는 반의어 1문항을 추가하고, 생략 이유는 생성 이력에 남깁니다.

기본 동시 처리는 2단어(최대 3단어)입니다. 단어별 생성과 AI 검수 후 오류 문항을 최대 한 번
자동 수정합니다. 통신 오류는 단계별 최대 두 번 재시도합니다. 모델 요청 제한 시간은 120초입니다.
형식 검증에서 종료된 작업은 문항별 오류 사유를 표시하며, `재개 · 실패 단계 재시도`를 누르면
기존 응답에서 오류 문항만 다시 수정·검수합니다. 빈칸 문항의 주관식 허용 답안은 필수입니다.
`AI 프롬프트 보기·수정`에서 공통·생성·검수·자동 수정 지침을 편집하고 선택 단어의 최종 System/User
프롬프트를 확인할 수 있습니다. 기본값 복원도 지원합니다. 편집 초안은 현재 앱 세션에서 유지되며,
생성 시작 시 기존 작업의 `config_json`에 저장합니다. 재개할 때는 해당 작업의 지침을 사용합니다.
문항 이력의 `실제 AI 전달 프롬프트 이력`에는 각 호출에서 사용한 System/User 내용을 표시합니다.

검수 완료분은 미리보기에서 수정·재검수한 뒤 `PostgreSQL에 문제 저장` 영역에서
`검수 완료 문제를 PostgreSQL에 저장`을 누릅니다. 저장 대기 단어·문항 수와 저장 위치를 표시하며,
문항을 기록한 뒤 검수 완료 내용과 일치하는지 확인하고 저장 결과를 표시합니다.
재생성 저장은 표시된 대상 단어의 기존 묶음을 교체하며 새 묶음에서 생략한 위치는 제거합니다.

화면을 이동해도 앱 프로세스가 실행 중이면 계속 처리합니다. 일시정지는 진행 중 응답을 기록한 뒤
적용되며, 앱 종료·백업 복원 후에는 생성 이력에서 재개합니다. 시험 대량 생성과 프로젝트 잠금을
공유하므로 동시에 실행하지 않습니다. 원본 단어나 기존 문항이 변경되면 저장 충돌을 표시합니다.

새 HTTP API는 없습니다. PostgreSQL `topik_bank.vocabulary_questions`에 문항을 저장하고,
기존 `data/bulk_generation.db`의 `vocabulary_batches`, `vocabulary_tasks`에 작업·응답을 기록합니다.
마이그레이션 `017_vocabulary_questions`는 로컬 DB 백업 후 적용합니다. 기존 미적용 마이그레이션이
있으면 먼저 확인해야 합니다. 화면의 `문제 기능 준비`도 관리 대상 로컬 DB에서만 실행됩니다.
이 기능의 생성·검수 테스트는 모의 모델과 임시 PostgreSQL DB를 사용합니다.

## 문제 해결

### `python3.11: command not found`

Python 3.11을 설치한 뒤 터미널을 다시 열고 `python3.11 --version`을 확인합니다.

### `Address already in use` 또는 포트 충돌

다른 포트로 실행합니다.

```bash
./.venv/bin/python -m streamlit run topik_question_lab/ui/app.py --server.port 8502
```

### macOS에서 스크립트 실행 권한 오류

README의 `sh setup_topik_lab.sh`, `sh run_topik_lab.sh` 형식으로 실행하면 실행 권한을 별도로 설정할 필요가 없습니다. 직접 실행하려면 다음 명령을 한 번 수행합니다.

```bash
chmod +x setup_topik_lab.sh run_topik_lab.sh
```

### ChatKHU 모델 자동 호출 실패

1. `.env`의 `CHATKHU_API_KEY`를 확인합니다.
2. 앱의 `모델 선택 > ChatKHU 전체 모델 동기화`를 실행합니다.
3. 계정의 허용 모델 목록에 해당 모델 ID가 있는지 확인합니다.
4. 자동 호출이 계속 실패하면 웹 수동 모드로 실행하고 JSON 응답을 붙여넣습니다.
